# style.css 정리 계획

디자인은 한 픽셀도 바꾸지 않고, 쌓인 덮어쓰기만 걷어내는 계획이에요.

## 1. 지금 상태 (재 본 숫자)

| | 숫자 |
|---|---|
| 전체 줄 수 | 8,026줄 (10월 30일 5,516줄 → 11월 1일 아침 6,891줄 → 지금) |
| `!important` 줄 | 544줄 |
| `:not(#na_x)`로 우선순위를 억지로 올린 줄 | 97줄 |
| 라이트 · 다크 양쪽에 거는 `body:is(.na_darkui, :not(.na_darkui))` | 120줄 |
| 같은 버튼(`na_v2_pillbtn`)을 건드리는 규칙 | 16군데 |

어디에 쌓였는지:

| 구간 | 줄 | `!important` | `:not(#na_x)` | 내용 |
|---|---|---|---|---|
| 1 ~ 2,470 | 2,470 | 89 | 0 | 원래 규칙. 패널 · 창 · 폰의 기본 모양 |
| 2,471 ~ 7,231 | 4,760 | 263 | 9 | 폰 앱들 + 창 v3 시안 반영 |
| 7,232 ~ 8,026 | **794** | **192** | **88** | 사흘 동안 창 하나 고칠 때마다 끝에 덧붙인 덮어쓰기 |

마지막 구간이 문제예요. 창을 고칠 때 원래 규칙을 고치지 않고 끝에 더 강한 규칙을 붙여서 이겼어요. 그래서 색 하나를 바꿔도 어느 규칙이 이기는지 매번 재 봐야 하고, "고쳤는데 안 바뀜"이 생겨요.

같은 파일 안에서 테마 변수(`--na-accent` 같은 것)를 정하는 곳도 네 군데예요(3줄, 1,137줄, 2,032 · 2,058줄, 3,413 · 3,428줄).

## 2. "안 깨짐"의 뜻

말로 "같아 보여요"가 아니라 기계로 증명해요. 세 가지가 전부 0이어야 한 단계가 끝나요.

1. **캡처 픽셀 비교 = 0픽셀 차이.** 정리 전 캡처와 정리 후 캡처를 ImageMagick `compare`로 빼요. 같은 브라우저 · 같은 글꼴이라 정확히 0이 나와야 정상이에요. 1픽셀이라도 다르면 멈춰요.
2. **계산된 스타일 비교 = 차이 없음.** 창 안 모든 요소의 색 · 배경 · 테두리 · 둥글기 · 여백 · 글자 크기 · 그림자 · 불투명도 등 30가지 값을 JSON으로 뽑아 정리 전후를 비교해요. 캡처에 안 잡히는 것(가려진 요소, 호버 · 포커스 · 비활성 상태)까지 잡아요.
3. **상태 강제.** 호버 · 포커스 · 눌림은 CDP `CSS.forcePseudoState`로 켜 놓고 2번을 한 번 더 떠요.

## 3. 안전망을 먼저 만들어요 (0단계)

CSS는 한 글자도 안 건드리고, 비교 도구와 기준 캡처부터 만들어요. `tools/dev/`에 넣어요.

**찍는 범위 (전부 라이트 + 다크):**

- 확장 창 24개의 처음 화면 (이미 자동으로 열리는 목록이 있어요)
- 결과 · 진행 화면: 섹션 버전, 제목 다시 짓기 결과, 섹션 합치기 결과, 마법사 2 · 3 · 4단계, 작업실 시작 전 · 대화 중 · ⋯ 메뉴 · + 메뉴, 아카이브에 질문 답, 고쳐 달라고 하기
- 빈 화면 6개 (대사 은행 · 누가 아는가 · 말투 지문 · 이탈 감지 · 분기 · X-ray)
- 확장 설정 패널 (펼친 상태)
- 휴대폰 홈 + 앱 첫 화면들 (폰 CSS는 이번에 안 고치지만, 안 깨졌다는 증거로 찍어요)
- 확인 팝업 (`na_confirm`) 두 종류

**찍는 조건:**

- 폰 크기 412×870, 그리고 넓은 화면 1,280×800 (`wide` 창이 넓을 때 모양이 달라요)
- ST 테마 3가지: 기본, Dark Lite, Cappuccino. `!important`와 `:not(#na_x)`는 대부분 ST 테마 CSS를 이기려고 넣은 거라, 다른 테마에서도 안 깨지는지 봐야 해요. 이게 제일 중요한 안전장치예요.

이러면 캡처 약 60장 × 2테마 × 3 ST테마 × 2크기 = 700장쯤이에요. 한 번 도는 데 10분 정도예요.

**도구 하나 더:** "죽은 규칙 찾기." CDP `CSS.getMatchedStylesForNode`로 창마다 모든 요소에 어떤 규칙이 붙는지, 그중 실제로 값을 정하는(이기는) 규칙이 뭔지 세요. 어디서도 한 번도 못 이기는 규칙은 지워도 화면이 안 바뀌어요. 지금 돌리는 중이고, 결과는 아래 4-1에 적어요.

## 4. 정리 순서

단계마다 커밋 하나, 캡처 비교 0, 계산 스타일 비교 0이에요. 하나라도 어긋나면 그 단계는 되돌리고 원인을 적어요. 전 단계가 끝나기 전엔 다음 단계 안 해요.

### 4-1. 죽은 규칙 지우기

- 죽은 규칙 도구가 "어디서도 안 이김"이라고 한 규칙만 지워요. 순수 삭제라 화면이 변할 수가 없고, 비교로 확인해요.
- 단, 도구가 못 여는 화면(작업실 속 상태 일부, 폰 깊은 화면)에서만 쓰는 규칙일 수 있어요. 그래서 지우기 전에 셀렉터의 클래스가 `src/*.js` 어디에도 없을 때만 "진짜 죽음"으로 쳐요. 둘 다 통과한 것만 지워요.
- 결과: (도구 결과 나오면 적음) 규칙 중 ___개가 죽어 있음.

### 4-2. 끝에 붙은 덮어쓰기를 제자리로 합치기

7,232줄부터 끝까지, 창별 블록을 하나씩 처리해요. 순서는 작은 것부터예요: 섹션 버전 → 제목 다시 짓기 → 작업실 → 마법사 → 원문 뽑기 → 빈 화면 6개 → 달력 · 키워드 · X-ray · AU → 공통(테두리 없애기 · 체크박스 · 둥글기 · 다크 차콜).

한 블록을 합치는 법:

1. 블록 안 규칙마다 "원래 자리"를 찾아요. 같은 요소를 그리는 규칙이 앞에 있으면 거기예요. (예: `.na_ly3_tool`은 7,367줄이 원래 자리, 7,978줄은 덮어쓰기)
2. 덮어쓰기의 값을 원래 규칙에 **써넣고** 덮어쓰기는 지워요. 라이트 · 다크가 다르면 원래 자리에 두 줄로 나란히 둬요.
3. 원래 자리가 없는 새 요소(이번에 새로 만든 타일 · 표 등)는 그 창의 블록 안으로 **옮겨요.** 끝이 아니라 그 창 자리에요.
4. 그 창의 캡처만 먼저 비교하고, 통과하면 전체를 돌려요.

### 4-3. 억지 우선순위 내리기

- `:not(#na_x)` 97개와 `!important` 544개를 하나씩 빼 봐요. 빼고 3가지 ST 테마에서 계산 스타일 비교를 돌려요.
- 빼도 같으면 그대로 빼요. 빼면 달라지면(= ST 테마 CSS를 이기려고 꼭 필요한 것) 다시 넣고, 그 줄 끝에 `/* ST: menu_button을 이김 */`처럼 **왜 필요한지** 한 줄 적어요.
- 목표는 0개가 아니에요. "이유가 적힌 것만 남기기"예요. ST 기본 CSS가 `!important`를 쓰는 곳(`.menu_button`, `.text_pole`, 팝업 버튼)은 우리도 써야 이겨요.

### 4-4. 테마 변수 한곳으로

- 네 군데에 흩어진 `--na-*` 정의를 파일 맨 위 블록 하나로 모아요: 기본값 → 라이트 → 다크 순서로요.
- 3.169.30에서 `body.na_darkui { --na-onaccent }`를 따로 붙여야 했던 이유가 변수가 `.na_popup` 안에서만 정의돼서예요. 맨 위 `body` 단위로 올리면 이런 구멍이 안 생겨요.

### 4-5. 파일 순서 다시 잡기

내용은 안 바꾸고 블록 순서만 이렇게 정렬해요. 블록을 옮길 때마다 비교를 돌려요 (CSS는 순서가 우선순위라, 옮기면 바뀔 수 있어요).

```
1. 변수 (라이트 · 다크)
2. 공통 부품 (버튼 · 칩 · 필드 · 체크박스 · 토글 · 카드 · 팝업 틀)
3. 확장 패널
4. 창 하나에 블록 하나 (가나다순, 머리말에 시안 폴더 이름)
5. 휴대폰 (이번엔 안 건드림, 통째로 뒤로)
```

### 4-6. 다시 안 쌓이게

- `tests/css.test.mjs` 추가: `!important` 수 · `:not(#na_x)` 수 · 파일 끝 100줄 안의 새 창 블록 수가 기준보다 늘면 테스트가 실패해요. 기준 숫자는 정리 끝난 값으로 박아요.
- `docs/DESIGN.md`에 규칙 추가: "창을 고칠 땐 그 창 블록 안의 원래 규칙을 고친다. 파일 끝에 덧붙이지 않는다. `!important`를 새로 쓰면 이유를 옆에 적는다."
- 창을 고치기 전엔 죽은 규칙 도구로 그 창의 규칙을 먼저 보고 시작해요.

## 5. 이번에 안 하는 것

- **휴대폰 CSS (370줄 + 배달 · 지갑 · 은행 등 앱들):** 양이 많고 덮어쓰기 문제는 창보다 덜해요. 창 정리가 끝난 뒤 같은 방법으로 따로 해요.
- **반영 코드:** 우리 몫이 아니에요.
- **디자인 변경:** 정리 중엔 색 · 여백 · 모양을 하나도 안 바꿔요. "이참에 이것도"는 안 해요. 고치고 싶은 게 보이면 적어 뒀다가 정리 끝나고 따로 물어봐요.

## 6. 위험한 곳과 대비

| 위험 | 대비 |
|---|---|
| 캡처에 안 나오는 상태(호버 · 포커스 · 비활성)가 바뀜 | 계산 스타일 비교 + 상태 강제. 캡처만 믿지 않아요 |
| 다른 ST 테마에서만 깨짐 | ST 테마 3가지로 돌려요. `!important`를 뺄 때 특히 |
| 도구가 못 여는 화면이 깨짐 | 그 화면에서만 쓰는 규칙은 4-3에서 우선순위를 안 내려요. 목록을 적어 두고 손으로 한 번 열어 확인해요 |
| 넓은 화면에서만 깨짐 | 1,280 너비도 같이 찍어요 |
| 순서를 바꾸다 우선순위가 뒤집힘 | 블록 하나 옮길 때마다 비교. 한 번에 여러 개 안 옮겨요 |
| 정리 중에 디자인 요청이 들어옴 | 정리 브랜치를 따로 파요. 디자인 요청은 메인에서 받고, 정리 브랜치는 그때그때 메인을 받아서 다시 비교해요 |

## 7. 진행 · 확인 방식

- 브랜치 `css-cleanup`에서 해요. 단계마다 커밋 하나, 메시지에 줄 수 변화와 비교 결과(0 / 0)를 적어요.
- 단계가 끝날 때마다 "정리 전 | 정리 후" 캡처 한 장과 숫자(줄 수 · `!important` · `:not(#na_x)`)를 보여 드려요. 차이가 0인 캡처라 똑같아 보이는 게 맞아요.
- 메인은 전부 끝나고 "메인 ㄱㄱ" 받은 뒤에만 올려요.
- 예상: 0단계(도구 + 기준 캡처) 반나절, 4-1 ~ 4-3 하루 반, 4-4 ~ 4-6 반나절. 줄 수는 4-1 결과를 보고 적어요. 덮어쓰기 구간 794줄의 절반 이상은 원래 자리에 합쳐지면서 사라질 거예요.
